# AEROVE 独立版本规范

面向两版维护者，先按产品变化选择版本，再核对安装与发行身份。规则与历史起点分开阅读，不能把历史候选号当作当前公开版本。

**本页导航** · [版本如何选择](#版本如何选择) · [预览、稳定和构建身份](#预览稳定和构建身份) · [应用内发现更新](#应用内发现更新) · [当前起点与来源](#当前起点与来源) · [每次发行的记录](#每次发行的记录)

适用于 AEROVE 标准版和 AEROVE Lite。两版各自维护版本、发行通道、安装编号和更新入口，不追随 FlClash 或内核的版本数字。

## 版本如何选择

用户看到的产品版本采用 `主版本.次版本.修订版本`，按实际交付内容中影响最高的一类升级；不按提交数量、日期或上游标签升级。

| 变更 | 升级规则 | 示例 |
| --- | --- | --- |
| 不兼容的数据、配置、对外接口或升级边界变化 | 主版本 +1，次版本和修订归零；写明迁移、兼容和回滚条件 | `1.4.2` → `2.0.0` |
| 兼容的新功能、完整能力扩展或用户可选择的新行为 | 次版本 +1，修订归零 | `1.4.2` → `1.5.0` |
| 缺陷修复、安全维护、兼容性修正及不改变功能契约的性能优化 | 修订版本 +1 | `1.4.2` → `1.4.3` |
| 文档、开发工具、CI 或目录治理，应用输入与行为未变 | 不创建应用版本、不重打包 | 保持产品版本，单独提交维护记录 |

内核更新按它对本产品造成的实际影响分类：修复可为修订版，新增产品能力为次版本，不兼容变化按主版本评估。
不能因为 Mihomo、meow-rs、历史 clash-rs 或 FlClash 升级了某一位就跟着升级同一位。`0.x` 同样必须说明兼容边界，不能用“开发阶段”掩盖破坏性变更。

## 预览、稳定和构建身份

- 预览阶段依次使用 `-alpha.N`、`-beta.N`、`-rc.N`；同一阶段的 N 从 1 单调递增。alpha 用于内部早期验证，beta 用于功能候选，rc 用于准备转稳定的候选。
- 缺陷修复发生在同一未发布候选中时递增该阶段编号；稳定版发布后再修复则升级修订版本，不能覆写已发布版本。
- 完成对应验收后移除预发布后缀进入稳定版。预发布和稳定状态必须与实际 Release 标志及更新通道相符；不能仅改后缀宣称完成验收。
- `+构建号` 是真实构建元数据，与功能版本分离。推广原 APK 保留原编号和 `BUILD_INFO.workflow`，发布运行另记；禁止把推广运行号写回 APK 或改写原三资产。
- 两产品共用 UI 契约，不共用发布节奏或版本计数；同步同一功能时各自依据本产品当前版本升级，不强行对齐版本数字。
- 共同界面和功能更新可以安排同批发行，仍须分别完成两版相关验收；各自独立的内核、平台或维护更新独立发行，不为同步日期或版本号重发另一版。

## 应用内发现更新

两版均检查同一产品全部已发布的新版本，包含正式版、Alpha、Beta 和 RC，不以本地或远端的预览标志过滤候选。提示选定的最新可升级版本后，由用户选择更新或取消；取消不下载或安装，不自动升级。

标准版与 Lite 的候选、安装包和签名保持隔离。按产品语义版本选择候选；Android 还要求安装编号严格递增，不提供语义版本降级。同一语义版本的更高安装编号可以提示更新。草稿、无效版本、错误产品或不可信资产不作为候选；请求或分页失败须报告检查失败，不能显示“已经是最新版”。

GitHub 的预览发布标志及标准稳定版 latest 继续表示发行状态；应用发现全部新版时读取产品发行列表，不依赖 stable latest。桌面跳转选定版本的实际发布页，不能发现测试版后仍打开稳定版 latest。

## 当前起点与来源

本节记录版本独立化时的历史起点：`0.10.0-beta.1` 是当时的候选选择，并非当前最新公开预览版；现行版本与发行状态见[标准版更新记录](../aerove/CHANGELOG.md)及各产品权威版本文件。

标准版已发布的 `0.9.1+2026102203` 及更早 `-X` 版本保留原样，不改名、重打包或重写历史资产。
下一项包含新增客户端功能的标准版候选采用 **`0.10.0-beta.1`**；它引用 FlClash `v0.9.2-pre.1` 的代码，但产品版本不再使用该上游编号。
Lite 首个候选继续采用 **`0.1.0-beta.1`**。候选号是开发目标，未通过验收、未上传正式资产时不能称为已发行。

| 产品 | 产品版本权威来源 | 安装与发行身份 |
| --- | --- | --- |
| AEROVE 标准版 | [pubspec.yaml](../../apps/aerove/pubspec.yaml) 的语义版本；由 `tool/aerove_version.py` 解析 | 保留 `com.follow.clash.dev` 与持久签名；安装编号为 `2026102200 + 原实际构建 GITHUB_RUN_NUMBER`；tag 为 `v<产品版本>+<安装编号>` |
| AEROVE Lite | [version.properties](../../apps/aerove-lite/version.properties) | 保留 `dev.aerove.lite` 与独立持久签名；`versionCode` 显式维护、在新发行构建前递增且不回退；tag 为 `lite-v<产品版本>+<versionCode>` |

包名、签名、安装编号与更新地址属于升级兼容边界，不能为了版本规则重置。编号必须高于该产品已发布的最高编号，处于 Android 允许范围内；仓库重建、工作流改名或计数重置时先验证已有发行记录，不能套用新计数后覆盖旧包。

FlClash 历史来源、Mihomo/meow-rs 及历史 clash-rs 固定提交、可重放补丁及依赖版本单独保留在产品的来源元数据和构建信息里。
产品版本独立不等于删除来源或放宽祖先、补丁、内容哈希与许可证校验。

## 每次发行的记录

发行前记录所属产品、当前稳定版本、拟发布版本、升级类别、具体内容与兼容影响，更新该产品权威版本文件和本次更新说明。
共享 UI/功能变化同时完成[双向契约](../shared/UI_CONTRACT.md)要求的另一版影响核对；单端未闭环不能靠独立版本号豁免。

通过分支验证后推广精确原产物；正式下载核对版本、来源、原构建、哈希、签名、包名、ABI 与说明，再归档该产品 CHANGELOG。
稳定标准版更新其稳定 latest；标准预览和全部 Lite 发行使用各自通道，不能抢占标准稳定更新入口。纯文档归档不触发新应用发行。
