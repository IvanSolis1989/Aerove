# 文档编写与视觉规范

[文档导航](../README.md) · [开发维护](README.md) · [仓库开发入口](../../AGENTS.md)

本规范是 AEROVE 人写项目文档的统一编写、排版和视觉验收依据，覆盖仓库 Markdown、文档入口及网站中英文内容。目标是清楚、精美、现代且便于维护；信息层次一致，不要求每一页复制首页。

## 信息层次

- 开篇给出主题、用途与适用范围，先说明读者能获得什么，再展开步骤或机制。使用准确的产品名称；中文、英文各自自然表达，共享事实保持一致，不靠逐句直译或遗漏限制来统一风格。
- 通常每页一个语义一级标题，正文按二级主题、必要的三级步骤展开，不跳级制造视觉大小。组合式代理入口、机器格式、发行历史及第三方原文允许保留其必要结构，不为单一标题规则破坏语义。
- 标题下提供简短分类导航，长文按主题提供页内目录。短文已有清晰入口时可保留，不机械增加目录、重复导读和页尾长链接墙。
- 使用自然段解释，有序列表表达操作，无序列表表达并行选项。段落、列表与代码块之间留空行；代码块标注语言，命令注明执行目录。不要为统一外观全仓重折行或更改代码与命令。
- 新文档进入现有 `docs/` 类别，并进入相应索引；工程和代理专用说明保留其既定发现位置。归属与归档遵循[仓库布局规则](REPOSITORY_LAYOUT.md)。临时日志、预览与截图证据保存在仓库外任务目录或 CI artifact。

## 页面模板

### 产品首页与分类入口

根 README 应让读者快速理解产品、找到下载并开始使用，包含以下信息：

1. 产品介绍与价值：说明用途、适用平台和两款独立产品的关系。
2. 下载与版本：正式安装包入口、发行说明和产品状态；稳定、预览与未首发状态明确区分。
3. 简明开始路径：从安装、导入自备配置到连接与基本检查，通常以三步组织。
4. 有来源的界面展示：图像与文字共同解释核心体验，注明展示范围。
5. 按需导航：使用说明、产品变化、开发维护、共享契约、交流与来源许可。

下载与开始入口按读者操作顺序安排，不必机械套用固定区块高度。密集参数、长矩阵、维护命令、排障和完整变更历史进入仓库二级页面或唯一事实源；不另建 Wiki 副本。分类入口只需用途、关键路径与下一步，不重复品牌 Hero、下载按钮和截图。

### 操作指南与模块说明

按“目标与范围 → 前提和执行目录 → 操作 → 预期结果与验证 → 问题定位及相关参考”组织。没有实际操作的说明不强行凑步骤；模块 README 先解释职责和所属产品，不把内部工程能力写成已经交付的用户功能。

### 契约、开发参考与研究

按“范围与权威级别 → 主题导航 → 规则或机制 → 验证边界 → 来源与相关入口”组织。研究额外分清固定来源、已确认结论与未闭环项。有效契约只有一份权威文件，产品说明只链接；不能复制较弱版本或通过改文档把未完成实现判为完成。

## 表格与提示

- 表格优先不超过三列，每表聚焦一种比较。宽表按主题、平台或用途分组；长说明放表外或改为字段列表，完整保留所有字段、条件与对应关系。
- 确实依赖多列关系的工程映射可以保留宽表，但须说明用途并验证窄屏阅读；不能为了凑三列删字段，也不能出现首列逐字竖排、极窄教程列或长代码塞进单元格。
- 重要状态和提示使用简短的文字标签或引用块，例如“适用范围”“尚未验证”“操作结果”。提示放在相关操作附近，不能只靠颜色、图标或大段加粗传递含义。避免整页警告框和重复强调；必须、禁止等规范强度保持准确。

## 图片与视觉

- 使用清晰标题、留白和克制的层次形成现代感。按钮与导航可采用连续圆角、柔光及适度的玻璃视觉，但不能每页堆大 Hero、重复 SVG 或全局装饰。静态柔光图不能声称具有真实动态折射。
- GitHub 文档遵循可用的 Markdown/GFM 能力，不依赖 inline CSS、JavaScript、外部字体或 GitHub 不支持的布局。网站可使用适合其实际运行环境的样式，保留键盘焦点、跳转主内容、主题/语言切换与减少动画偏好。
- 使用可读的正文字号、行高和字体回退，浅深色下文字、链接、按钮和图中标签保持足够对比；不能通过缩小文字、降低画质或隐藏内容解决窄屏溢出。
- 正式文档静态资源放 `docs/assets/`，复用已有合适资产。图片必须有说明内容的 alt；图内文字、按钮目的和关键信息在附近提供同等可搜索的文字与链接回退，不用一张大图承载全部说明。
- 展示图注明产品、来源、适用版本或源码身份、运行环境和状态；明确离线组件树渲染、模拟器、真实 Android、设计稿各自边界。旧样图未经验证不能当作当前完整界面，部分组合不能当作完整十二组合验收。

## 事实与兼容

- 命令、代码、字段、固定 SHA、金额及其他关键数值、授权、优先级、禁止事项与权威条款必须准确保留。格式美化不能降低验收门槛、改变运行行为或制造新授权。
- 发行条目和机器读取字段遵循既有消费者格式；生成文件从权威源生成，不能直接改写兼容更新入口。历史记录、第三方许可证、版权与署名保留原文，必要时只在外围增加历史或来源说明。
- 保持既有路径和锚点兼容。更改标题前检查入站片段链接，必要时保留显式旧锚点；移动文件必须修复引用，先检查源码、CI 和已发行客户端消费者。不要为美观无目的重命名或重排归档。
- 发布事实、候选产物、研究结论、静态检查、真实功能、Android 渲染和能耗实测分开标注。进程存活、静态映射、截图或模拟结果不代替对应验收，不宣称尚无实测依据的省电收益。
- 所有实际参照、复制或适配的开源来源统一登记到[开源来源与鸣谢](upstreams.md#开源来源与鸣谢)，含固定版本或提交、用途与采用方式；不另建漂移名单。文档样式参考也遵守该要求。

## 验收与交付

### 推送前

修改文档内容、布局、表格、媒体或导航后，必须对受影响的代表模板进行真实 GitHub GFM 或等效渲染检查：**桌面 1280px、手机 390px，分别浅色与深色，共四组合**。网站涉及中英文时，两种语言都需检查。代表页应覆盖本次变化与具体风险，例如长表、长路径、SVG 或提示块，不以首页通过代替所有模板。

确认页面整体无横向溢出、文字和图形无裁切、图片无断链、按钮与导航可读且可操作；必要的代码/技术表格局部滚动不得使页面整体溢出。对照实际视觉查看截图，不能只凭宽度数字、生成器检查或静态源码通过。

核对所有本地文件链接和页内锚点，包含引用式链接、中文标题、显式锚点和重名标题；网站检查生成目录的资源与动态入口。新增或改变的下载 URL 检查真实响应及对应发行资产。输入、内容和地址未变且已有充分证据时复用检查，只补验受影响部分，不机械全量重跑。

### 现有检查入口

在仓库根目录执行布局和文档入口检查：

```sh
python tooling/workspace.py check
```

网站已有生成链位于 `tooling/website/build_site.sh` 与 `tooling/website/render_site.mjs`，页面及中英数据位于 `website/`。沿用现有链和可用环境，不为文档美化擅自安装依赖或新建常驻服务。完整网站构建脚本使用固定元数据文件或读取 GitHub 发行信息，并拒绝已存在的输出目录；运行前选择本次尚不存在的专用输出目录。

本地链接、浏览器预览和截图可复用已可用工具；仓库未提供统一 Markdown 渲染或全锚点检查命令时，交付中记录实际使用的方法、输入和限制，不虚构一个已经存在的检查工具。布局检查不能替代渲染、片段与网站运行验收。

### 推送后与证据

仅按本次授权提交、推送或发布。推送后核对实际 GitHub 文档渲染和相关提交 CI；涉及已部署网站时，检查真实站点的对应页面与语言。不能用本地预览冒充线上验收；若网站未部署或检查未完成，如实列出状态，不自行扩大为部署授权。

交付记录受影响文件、原样保留项及理由、检查结果和证据位置，必要时保留前后哈希、截图、来源身份与未解决项。纯文档和静态视觉变更不重编 App、不改变已验收 APK 身份；若同时涉及真实应用行为，按对应产品规则完成其验证。
